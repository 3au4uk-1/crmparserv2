# Связка сделок: родитель + сметы — Design Spec

**Дата:** 2026-09-16  
**Статус:** Approved for planning  
**Репозитории:** `crmparserv2` (идентичность, группы, парсинг, печать/расход), `BrandingTwentyView` (доска реализации, модалка)

## Проблема

Менеджеры в Bitrix заводят несколько карточек на одну коммерческую работу и/или пишут несколько броней Tony в одном названии. Парсер и Twenty сейчас живут в модели «одна бронь = одна сделка = один Bitrix»:

- Несколько броней в названии режутся на отдельные Twenty-сделки; часть броней не создаётся (пустой Tony, отмена старого `twenty_id` при появлении нескольких номеров).
- Несколько Bitrix на одну бронь затирают `crm_lead_id` — остаётся последняя ссылка.
- На доске реализация видит разрозненные карточки; табло и маржа врут.
- Печать/фрезер/расход берут `bitrixLink` той карточки, на которой позиция, а не оплатной.

Живые примеры:

- **А7 / Титова / 1–2 сент:** четыре Bitrix + четыре брони (`189820`, `190321`, `190324`, `190326`) — одна работа. Деньги на «Для оплаты», позиции и часть расхода на доп.точках.
- **Маковецкая / кейтеринг:** пять броней в одном названии, в Twenty попали две.
- **Бронь `111111`:** две и более ссылок Bitrix (оплата, бронь, ещё карточка) на один заказ Tony.

## Цели

- Не терять брони, позиции, Bitrix- и Tony-ссылки.
- На доске реализации одна строка на коммерческую работу; внутри — отдельные сметы.
- Связывать автоматически с ручной подгонкой (модалка), без тихого merge.
- Печать, фрезер и расход идут на канонический Bitrix (оплатной / выбранный).
- Цифры родителя — реальная выручка и маржа, без двойного счёта и без потери уже повешенного расхода.

## Не цели (v1)

- Тихий автомердж без подтверждения в модалке.
- Склейка одинаковых позиций между сметами (0 ₽ на точке и цена на оплатной остаются разными строками).
- Перепись уже выгруженных строк печати/фрезера (append-only, как сейчас).
- Отдельный Twenty-объект «группа» вместо opportunity-родителя.
- Скрытие детей в нативном списке Opportunities Twenty (только доска реализации).
- Использование стадии `DUBL` как связи.

## Зафиксированные решения

| Тема | Выбор |
|------|--------|
| Модель | Отдельный родитель (новая opportunity) + живые сметы |
| Смета | Одна бронь Tony = одна смета; N ссылок Bitrix на ней |
| Группа | Несколько броней / несколько коммерческих карточек → родитель |
| Имя родителя | Вручную или авто с канонической сметы; ручное имя не перезаписывать |
| Канон сметы | С поступлением, иначе макс. выручка, иначе вручную в модалке |
| Канон Bitrix | Среди ссылок канон-сметы (и группы): с поступлением → иначе вручную |
| Автопереключение канона | Только если не закреплён вручную; две оплаты → только модалка |
| Автоподсказки | Жёсткие + мягкие; запись группы только после подтверждения |
| Доска | Одна строка родителя; сметы в раскрытии; дети не в общем списке |
| Выручка родителя | Σ `amount` всех смет |
| Поступления / расход | Только канон; при связке уже висящий расход детей переезжает на канон один раз |
| Печать / фрезер | Позиция со сметы, в таблицу — Bitrix канона и имя родителя |
| SoT группы | Парсер (`deal_groups`); Twenty — зеркало для доски |

## 1. Слои

```
Календарь Bitrix          Tony заказ
   │                         │
   ├─ N lead id ─────────────┤
   └─ брони в title ─────────┘
              │
              ▼
     parser deals (смета = booking#N)
     deal_bitrix_links[]
              │
              ▼
     deal_groups (подтверждённые)
              │
              ▼
     Twenty: parent opportunity
             child opportunities (сметы, parentOpportunityId)
```

1. **Смета в парсере** — строка `deals` с ключом `booking#<n>`. Позиции из Tony (фолбэк календарь). Список Bitrix не затирается.
2. **Смета в Twenty** — opportunity 1:1 с парсерной сметой: позиции, `tonyLink`, все Bitrix в `bitrixLink` (primary + secondary).
3. **Родитель в Twenty** — отдельная opportunity без позиций. Агрегаты и имя. У смет `parentOpportunityId`.

Канон — флаг на смете и на одной её Bitrix-ссылке, не сам родитель. Смена канона не создаёт нового родителя.

## 2. Два ортогональных кейса

| Сигнал | Что это | Действие |
|--------|---------|----------|
| Одна бронь, несколько Bitrix | Оплата / бронь / ещё карточка на одном Tony | Одна смета, много B-ссылок |
| Несколько броней, один заказ | А7; несколько номеров в одном title | Родитель + несколько смет |

Они складываются: у родителя несколько смет, у каждой одна Tony и N Bitrix.

Жёсткое совпадение броней **не** делает две сметы, если номер один: это кейс ссылок, не группы.

## 3. Данные парсера

### `deal_bitrix_links`

| Колонка | Смысл |
|---------|--------|
| `deal_id` | Смета |
| `bitrix_id` | ID сделки Bitrix |
| `role` | `payment` \| `booking` \| `other` |
| `is_canonical` | Канон **этой** сметы (для группы канон задаётся на группе) |
| UNIQUE `(deal_id, bitrix_id)` | Парсинг дописывает, не затирает |

`deals.crm_lead_id` остаётся совместимым зеркалом **канонической** ссылки сметы (не единственным хранилищем).

### `deal_groups` / `deal_group_members`

| Колонка | Смысл |
|---------|--------|
| `twenty_parent_id` | Opportunity-родитель |
| `name` | Имя на доске |
| `name_locked` | `true` после ручного имени |
| `canonical_deal_id` | Канон-смета |
| `canonical_bitrix_id` | Канон-Bitrix: обязан быть в `deal_bitrix_links` канон-сметы |
| `canonical_locked` | `true` после ручного выбора в модалке |
| members | `deal_id` смет, UNIQUE на `deal_id` (смета в одной группе) |

Развязка удаляет membership; пустая группа удаляется; сметы и их `twenty_id` не трогаем.

## 4. Twenty

- Self-relation на opportunity: `parentOpportunityId` (дети → родитель).
- Родитель: нет line items; `amount` = Σ выручек смет (не `OTMENA`); поступления и расход — с канон-сметы после переноса.
- `bitrixLink` сметы: primary = канон этой сметы (её «главная» B), secondary = остальные. Все URL сохраняем.
- Родитель может нести primary Bitrix/Tony канона как ярлык; источником правды ссылок остаются сметы.
- Стадия `DUBL` не используется для связи.

Нативный список Opportunities по-прежнему показывает детей — ограничение v1.

## 5. Парсинг и идентичность

Текущее «несколько броней → N `deals`» остаётся. Меняется потеря данных:

- Все валидные номера из title дают сметы. Пустой/404 Tony **не** дропает бронь: смета живёт, позиции с календаря или со следующего успешного Tony.
- Появление нескольких броней у уже синкнутой `#cal` сделки **не** отменяет её `twenty_id`: релинк/разнесение без cancel, затем кандидат в группу.
- Два календарных события с одной бронью `111111` → один `deals`, две строки в `deal_bitrix_links`, обновление `crm_lead_id` только если канон сметы ещё не закреплён.
- Подтверждённую группу повторный парсинг не собирает заново и не разваливает. Подсказка для *несвязанных* кандидатов может появиться снова.

## 6. Подсказки и модалка

**Жёсткие** (верх списка): пересечение броней между карточками; несколько броней в одном Bitrix-событии.

**Мягкие** (ниже, без автозаписи): общий клиентский маркер в названии (например «А7») + тот же менеджер + соседние даты загрузки/события.

Смета уже в группе A, жёсткий сигнал тянет в B → предложение в модалке, не слияние групп.

Модалка на доске реализации:

1. Набор смет (чеки, поиск, подсказки).
2. Имя родителя (дефолт — название канон-сметы).
3. Канон-смета и канон-Bitrix (дефолт по правилам; можно сменить).
4. Связать / снять смету / распустить группу.

Запись идёт в API парсера, парсер зеркалит Twenty. Доска не пишет группу только в CRM.

Права: те же, кто ведёт реализацию.

### Дефолты, чтобы не двоилось чтение

- **Роль Bitrix-ссылки:** есть поступления по этому `bitrix_id` или в названии события есть «оплат» → `payment`, иначе `booking`. В модалке можно сменить на `other`.
- **Мягкий маркер:** токены названия без кодов компании, дат и номеров броней; общий токен длины ≥ 2 (как «А7»). Менеджер — `manager_name`. Даты: пересечение `[load_date − 2д; load_date + 2д]` (нет `load_date` → `start_date`).
- **Метаданные родителя:** `company`, `loadDate`, менеджер/«взял» копируются с канон-сметы при создании и при смене канона, если поле на родителе ещё не правили вручную.
- **Две оплаты:** не выбирать канон автоматически, даже если одна сумма больше.

## 7. Деньги

```
parent.amount        = Σ smeta.amount          // неотменённые позиции, как сегодня
parent.summaPostupleniy = canonical.summaPostupleniy
parent.rashod*       = canonical.rashod*
parent.margin        = parent.amount − parent.rashodItogo
```

Поступления с неканонических смет в родителя **не** суммируются (защита от размножения платежа одного Bitrix-события на N броней).

При **подтверждении связи** расход, уже записанный на члены группы, переносится на канон один раз (ключ — Bitrix ID / строка источника, без двойного счёта). Пример А7: 34 870 + 9 179 + 2 400 → канон.

Новые синк-расходы после связи пишутся только на канон-Bitrix / канон-смету / родителя (один Twenty-id для `rashod*`).

## 8. Печать, фрезер, расход

- Триггер и позиции — без изменений (стадия позиции на смете).
- В строку таблицы: имя **родителя** (если есть группа), ссылка Bitrix **канона**.
- Постоплата без поступлений: канон = смета с макс. выручкой → экспорт идёт.
- Старые строки со ссылкой доп.точки не переписываем.

Резолв канона делает парсер (у него `deal_groups`) в момент экспорта/синка расхода.

## 9. Доска реализации

- Список: opportunity без `parentOpportunityId`, плюс родители; дети скрыты.
- Раскрытие родителя: сметы, позиции, все T/B ссылки, суммы сметы.
- Действие «Связать сделки» → модалка. С несгруппированной сделки можно стартовать набор.
- Табло использует агрегаты родителя, не сумму видимых строк детей.

## 10. Потоки

**Парсинг → синк смет** как сейчас (плюс список Bitrix и запрет дропа броней).

**Подтверждение группы:** `deal_groups` → создать/обновить parent opportunity → проставить `parentOpportunityId` → пересчитать агрегаты → перенести расход → дети пропадают из списка.

**Развязка:** снять `parentId`, вернуть в список; родитель без детей удалить только как родителя.

**Смена канона:** обновить флаги, агрегаты, зеркало `crm_lead_id` / primary bitrix родителя; печать дальше идёт на новый канон.

**Появление оплаты** на другой смете при `canonical_locked = false`: канон переключается на оплатную. Если locked — только подсказка в модалке.

## 11. Ошибки

- Tony down / 404: не clobber сметы, не cancel, не развал группы.
- Две сметы с поступлениями: канон не выбирается сам.
- Сбой зеркала Twenty: парсерная группа остаётся SoT, догон в следующем прогоне.
- Конфликт membership: модалка, не overwrite.

## 12. Проверка

Юниты парсера: 1 бронь × 2 Bitrix; 5 броней в title без cancel `twenty_id`; пустой Tony не дропает; жёсткие/мягкие кандидаты без записи; подтверждённая группа стабильна; деньги и перенос расхода; locked канон.

Доска: дети скрыты; раскрытие; модалка; печать с канон-Bitrix.

Живой регресс: А7 (4 сметы, 4 Bitrix, позиции на месте, расход на каноне); Маковецкая (все брони как сметы); `111111` (две B на одной смете).

## 13. Вне scope, но рядом

- Скрытие детей в стандартном каноне Twenty.
- Автопереименование родителя по шаблону «клиент + даты» сверх дефолта с канон-сметы.
- Миграция исторических `DUBL` в группы.
