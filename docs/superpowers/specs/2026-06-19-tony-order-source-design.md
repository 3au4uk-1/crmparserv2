# Tony как источник истины по заказу — дизайн

**Дата:** 2026-06-19
**Статус:** Утверждён к написанию плана реализации
**Ветка разработки:** `test/local-dev` (тестируем локально, на прод не выкатываем до подтверждения)

## Контекст и проблема

Сейчас парсер (`backend/src/services/parser.js`) получает **все** данные из внутреннего календаря (Bitrix):
`authenticate()` → `fetchEvents(start, end)` → для каждого события `fetchDescription(eventId)` (HTML) →
`parseDealDescription` + `parseDealTitle` → запись в `deals` + `deal_items` → синк в Twenty.

Данные в брони `crm.apihide.com` (далее **Tony**) — по сути те же, но в другом формате, более актуальные и
структурированные: **отдельно цена за единицу и количество**, есть **Дата загрузки** (нужна, чтобы готовить
заказ вовремя). Авторизация в Tony — по логину/паролю (в отличие от куки-сессии Bitrix у календаря).

**Цель:** календарь используется только как список сделок (какие заказы существуют в периоде и их `title`),
а данные по заказу берём из Tony, делая Tony источником истины.

## Результаты исследования живого Tony

- **Логин:** `POST /auth/` (поля Логин/Пароль) → сессия-кука.
- **URL заказа:** `/orders/orders_edit/?id=<bookingNumber>` — страница **полностью server-rendered**
  (позиции и даты присутствуют в HTML, JS не требуется). Номер заказа = номер брони (`data-id`).
- **Позиции:** в `#order_products_list`, колонки `Название | Комментарий | Количество | Ед.изм. | Цена ₽ |
  Скидка % | ... | Итого ₽`; разбиты по категориям через `data-var`: `products`, `tech`, `food`,
  `personnel`, `sklad`.
- **Даты (имена полей):** `date_install` (+`date_install_time`) — **это и есть «Дата/Время загрузки»**;
  `date_event_begin` / `date_event_end`; `date_deinstall` (+`date_deinstall_time`);
  `work_time_begin` / `work_time_end`.
- **Несуществующий заказ** → HTTP 404 (естественная проверка валидности номера брони).

## Выбранный подход

**Подход A — Tony как слой обогащения поверх календарного парсера.** Календарь остаётся источником
обнаружения сделок; Tony встраивается как источник данных по заказу, с фолбэком на календарь. Вся
Tony-логика изолирована в новых модулях; запись в сделку остаётся в одном пайплайне (без второго писателя).

Отклонены: B (Tony основной, календарь только индекс) — ломает нужный фолбэк и требует крупного рефактора;
C (отдельный развязанный Tony-синк) — две точки записи в одну сделку, гонки, дублирование логики.

## Источник истины (карта полей)

**Из календаря (без изменений):**
- наличие сделок в периоде (какие заказы существуют);
- `title` → `company_code`, `manager_name`, номера броней;
- контакты: `contact_name`, `contact_email`, `contact_company`, `contact_phone`;
- `legal_entity`, `invoice_number`, `status`.

**Из Tony (источник истины, когда сделка слинкована с заказом):**

| Tony | Наше поле |
|---|---|
| позиции `#order_products_list` (все категории) | `deal_items`: `name`, `price` (цена за ед.), `quantity`, `discount %` → затем классификатор брендинга |
| `date_install` + `date_install_time` | `load_date` + `load_time` (**Дата/Время загрузки**, новое) |
| `date_event_begin` / `date_event_end` | `start_date` / `end_date` |
| `date_deinstall` + `date_deinstall_time` | `dismantle_time` (дата + время) |
| `work_time_begin`–`work_time_end` | `work_time` |
| адрес / место | `address` / `venue_type` |
| бюджет | Twenty `amount` = Σ(цена × количество) по брендинговым позициям |

Категории позиций: импортируем **все** (`products`, `tech`, `food`, `personnel`, `sklad`), решение о
брендинге принимает существующий `classifyItems`.

## Архитектура и поток данных

Обновлённый `runParsing(start, end)`:

1. **Discovery (календарь, как сейчас):** `authenticate()` (Bitrix) → `fetchEvents(start, end)`.
2. **Резолв броней:** для каждого события извлекаем **все** номера броней из `title`
   (`extractBookingNumbers` — массив, а не последний номер).
3. **Выбор источника на сделку:**
   - Валидная бронь (Tony вернул заказ, не 404) → `data_source = 'tony'`: тянем заказ из Tony, парсим
     позиции (все категории) + даты + адрес + бюджет.
   - Нет брони / 404 / Tony недоступен → `data_source = 'calendar'`: текущий парсинг описания календаря.
   - Несколько броней → отдельная сделка на каждую (см. «Модель данных»).
4. **Классификация:** позиции прогоняются через существующий `classifyItems` (без изменений).
5. **Синк в Twenty:** существующий `syncDealToTwenty` + новое поле «Дата загрузки» + бюджет из позиций Tony.
6. **Отмены:** `calendar-missing` работает по новой идентичности (исчезла бронь → отменяется именно та сделка).

**Поведение перехода (требование пользователя):** пока нет связи с Tony — данные из календаря; если на
повторном парсинге в `title` появляется номер брони — данные начинают браться из Tony.

**Аутентификация — два независимых провайдера:**
- Календарь: текущий `auth.js` (Bitrix, куки/логин) — без изменений.
- Tony: новый `tony-auth.js` — `POST /auth/` логином/паролем → своя сессия-кука и keep-alive.
  Настройки `tony_base_url`, `tony_login`, `tony_password` в `settings`.

## Модель данных и реконсиляция

**Проблема:** `deals.crm_event_id` сейчас `UNIQUE` (одно событие = одна сделка), что несовместимо с
«несколько броней → отдельные сделки».

**Новая идентичность сделки:**
- Новая колонка `deal_key TEXT UNIQUE`:
  - `"<crm_event_id>#<booking_number>"` для Tony-сделок;
  - `"<crm_event_id>#cal"` для фолбэка из календаря.
- Снять `UNIQUE` с `crm_event_id` (оставить обычным индексом — сделки группируются по событию).
- Новые колонки: `data_source TEXT` (`'calendar'`|`'tony'`), `load_date TEXT`, `load_time TEXT`.
- Миграция в `db/migrate.js`: бэкфилл
  `deal_key = crm_event_id || '#' || COALESCE(tony_order_id,'cal')`, пересоздание уникального индекса
  (SQLite — через `CREATE UNIQUE INDEX` или пересоздание таблицы).

**Реконсиляция на каждом парсинге (для одного события):**
1. Вычислить «желаемый набор» ключей: валидные брони → ключ на каждую (`tony`); иначе один ключ `#cal`.
2. **Переход cal → tony без потерь:** если раньше была ровно одна `#cal`-сделка и теперь ровно одна бронь —
   **релинкуем ту же строку** (обновляем `tony_order_id`, `data_source`, `deal_key`), сохраняя
   `approval_status`, `twenty_id` и ручные `sync_override` по позициям.
3. Иначе: создаём недостающие Tony-сделки; сделки события, чьих ключей больше нет в «желаемом наборе»,
   отправляем в отмену (существующая `cancelDealInTwenty`).
4. Позиции пишем через существующий `replaceDealItemsPreservingOverrides` (ручные переопределения сохраняются).

**Детект изменений:** `content_hash` для Tony-сделки считается по нормализованному снимку Tony
(позиции + даты + бюджет); для календарных — как сейчас (по описанию). Не изменилось → `skip`.

## Модули и компоненты

Новые файлы (изоляция Tony-логики):
- **`tony-auth.js`** — сессия Tony: `POST /auth/` логином/паролем, кука, keep-alive, повторные попытки,
  чтение настроек `tony_*`.
- **`tony-client.js`** — `fetchOrder(bookingNumber)`: GET `/orders/orders_edit/?id=<n>` через сессию Tony;
  возвращает HTML или `null` при 404/не найдено; таймауты + троттлинг.
- **`tony-parser.js`** — `parseTonyOrder(html)` → `{ items[], dates, address, venue, budget }`. Позиции по
  всем категориям с раздельными ценой/количеством/скидкой; даты по известным `name`/`id`.
- **`booking-numbers.js`** (или расширение `title-parser.js`) — `extractBookingNumbers(title)` → массив всех
  номеров (сейчас возвращается только последний).

Изменения в существующих:
- **`parser.js`** — оркестрация: резолв броней → выбор источника → реконсиляция. Календарная ветка не меняется.
- **`config.js`** + **`.env.example`** — `tonyBaseUrl/Login/Password`.
- **`twenty-opportunity.js`** — добавить «Дату загрузки» в `buildOpportunityInput`.
- **`frontend/src/pages/Settings.jsx`** — поля доступа к Tony.
- **`classifier.js`, `deal-items-update.js`, `twenty-sync.js`** — без изменений (переиспользуются).

## Twenty

- `name` = `title` (из календаря); `amount` = Σ(цена × количество) по брендинговым позициям Tony.
- `tonyLink` — уже существует (`twenty-opportunity.js`).
- **Новое кастомное поле** «Дата загрузки» (тип DATE_TIME) на Opportunity; создаётся в Twenty и добавляется в
  `buildOpportunityInput` из `load_date` + `load_time`.
- `arrivalTime/readyTime/workTime/dismantleTime` — заполняются из дат Tony (для Tony-сделок) или из
  календаря (для фолбэка).

## Обработка ошибок и устойчивость

- **Tony недоступен / логин не прошёл:** парсинг **не падает** — все сделки прогона обрабатываются как
  `calendar` (фолбэк). **Не** запускаем переход cal→tony и **не** отменяем существующие Tony-сделки (иначе
  массовая отмена из-за временного сбоя). Сбой логируется и виден в `parse_runs`/UI.
- **Заказ 404 / не найден:** номер считается невалидным → фолбэк на календарь для этой сделки; при нескольких
  номерах невалидный пропускается. Логируется.
- **Ошибка парсинга конкретного заказа:** логируем и продолжаем, не прерывая весь прогон.
- **Троттлинг:** задержка между запросами заказов в Tony (по образцу `delay(350)` у календаря).
- **Идемпотентность:** `deal_key` стабилен; `content_hash` пропускает неизменённое; `sync_override` сохраняются.
