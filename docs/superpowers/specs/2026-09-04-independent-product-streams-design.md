# Независимые потоки брендинга, декора и МК

**Дата:** 2026-09-04  
**Статус:** Утверждён к написанию плана  
**Репозитории:** `crmparserv2` (классификация, синк, миграция), `BrandingTwentyView` (поле, фильтр досок)  
**Ветка:** `staging`

## Проблема

После появления ключевых слов декора и МК позиции классифицируются одним значением `productStream` с приоритетом **МК → декор → брендинг**. Если имя матчится и на брендинг, и на декор/МК, позиция целиком уходит на доску «МК и Декор». На «Реализации» заказа нет.

Пример: [АРЕНДА/9.09/…СтойкаРегистрации+Брендинг…](https://twenty.dosugmayak.ru/object/opportunity/a0ee5617-726e-47d8-8e30-fbf171783075)

| Позиция | Сейчас | Нужно |
|---|---|---|
| Стойка барная Laconismo - внешняя оклейка корупса | `DECOR` | `DECOR` + `BRANDING` |
| Стойка барная Laconismo черный | `DECOR` | `DECOR` + `BRANDING` (если слова брендинга тоже сработали) |

Доска «Реализация» показывает только `BRANDING` (и historically `null` как брендинг). Доска «МК и Декор» — `DECOR` \| `MK`. Одна запись, два фильтра — пересечение должно быть видно **на обеих** досках.

Смена кода без миграции **не поднимает уже уехавшие заказы**. Это главный риск задачи.

## Цели

- Списки ключевых слов независимы: сработало направление — позиция видна на его доске.
- Пересечение: **одна** запись line item, стадия и правки общие, видно и в реализации, и в «МК и Декор».
- После выката существующие сделки в Twenty получают новый набор потоков. Пример со стойкой снова на реализации, не теряя доску декора.
- `null` / пустой набор больше не считается брендингом.

## Не в scope

- Новые доски или разделение «МК» и «Декор» на две страницы.
- Правка самих ключевых слов оператором (кроме того, что миграция пересчитает по **текущим** спискам).
- Повторный LLM-парсинг, смена `content_hash`.
- Print sheet / фреза / оклейка как отдельные ветки учёта.
- Копии позиций «для каждой доски».

## Контекст

| Что | Как сейчас |
|---|---|
| Классификация | `classifyProductStream`: первое совпадение MK, иначе DECOR, иначе BRANDING, иначе `null` |
| Допуск в Twenty | `resolveItemProductStream` ≠ `null`; автобрендинг: `keyword_match` / `llm_confirmed` без блеклиста брендинга |
| Хранение | Twenty `dealLineItem.productStream`: SELECT, одно из `BRANDING` \| `DECOR` \| `MK` |
| Доски | `normalizeProductStream`: всё кроме DECOR/MK → BRANDING; фильтр по одному значению |
| Скан декора/МК | scoped sync пишет `DECOR`/`MK` и **снимает** позицию с реализации |

## Подход

Набор потоков на позиции, не победитель.

Отклонено: флаги «ещё и на реализации» при живом SELECT (два источника истины); матч слов на лету на доске (нужны списки парсера, LLM и ручные включения разъедутся, старые записи сами не исправятся).

## Набор потоков

Тип: множество `{ BRANDING, DECOR, MK }`.

Поле в Twenty: то же `productStream`. Цель — **MULTI_SELECT** (массив `BRANDING` / `DECOR` / `MK`). Если `yarn twenty apply` на staging не меняет SELECT на MULTI_SELECT — добавить `productStreams` и читать его на досках; старый скаляр заполнять любым значением из набора только для карточки CRM, не для фильтра досок.

Доски читают набор. На переходный период до конца backfill: если набор ещё скаляр (старые записи), трактовать как массив из одного значения. Это **не** возвращает `null` к брендингу: `null` и `[]` никуда не кладём.

Карточка CRM может показывать чипы потоков. Ручная правка поля пишет набор; следующий синк парсера перезапишет по правилам ниже (как сейчас перезаписывает SELECT).

## Классификация (парсер)

`classifyProductStream` возвращает **массив** (возможно пустой), без приоритета между направлениями.

Для имени позиции:

1. Слова МК и не блеклист МК → добавить `MK`.
2. Слова декора и не блеклист декора → добавить `DECOR`.
3. Слова брендинга и не блеклист брендинга → добавить `BRANDING`.
4. Иначе, если `classification` ∈ {`keyword_match`, `llm_confirmed`} и не блеклист брендинга → добавить `BRANDING`.
5. `sync_override = include` и набор пуст → `[BRANDING]`.
6. `sync_override = exclude` → не в Twenty.

Блеклист одного направления не вычёркивает другие. Позиция в Twenty, если набор не пуст.

`getItemsForTwenty` / `enrichDealItems` несут `productStreams: string[]` (и на переходный период скаляр для логов: любое значение из набора, не использовать как фильтр досок).

### Scoped-скан декора/МК

После этой задачи скан **не имеет права** затирать набор одним `DECOR` или `MK`. Он по-прежнему отбирает сделки, где в наборе есть `DECOR` или `MK`, и синкает эти позиции, но в Twenty пишет **полный** набор, включая `BRANDING`, если брендинг тоже сработал. Иначе миграцию откатит следующий скан.

Отбор «есть DECOR или MK» — пересечение набора с `{DECOR, MK}`, не равенство скаляра.

## Доски (BrandingTwentyView)

- Реализация: набор **содержит** `BRANDING`.
- МК и Декор: набор содержит `DECOR` или `MK`.
- Пустой набор / неизвестное значение: **ни на одной** доске (не подставлять брендинг).
- Счётчики и суммы доски — по видимым на этой доске позициям. Пересекающаяся позиция входит в итоги обеих досок; в CRM сумма opportunity по-прежнему по всем line items сделки.
- Стадия, количество, комментарии — одна запись.

Тесты фильтра: только брендинг; только MK; только декор; пересечение брендинг+декор (пример стойки); `null` не на реализации.

## Миграция существующих сделок (обязательный результат)

Код досок и классификатора **не считается выкаченным**, пока существующие позиции в прод-Twenty не переписаны. Иначе заказы вроде стойки остаются только на «МК и Декор».

### Почему недостаточно деплоя

1. В Twenty уже лежат скаляры `DECOR` / `MK` / `BRANDING` / `null`.
2. Обёртка `DECOR` → `["DECOR"]` **не возвращает** брендинг: пересечение надо **пересчитать по текущим спискам слов**.
3. Обычный парсинг не трогает сделки с тем же `content_hash`.
4. Кнопка «Применить фильтры» / bulk-resync гоняет полный diff (create/delete, суммы, стадии). Для починки потока это лишний риск. Скан декора/МК в старом виде как раз **создал** дыру.

### Что мигрировать

Все сделки парсера с `twenty_id`, `approval_status != 'rejected'`, у которых есть хотя бы одна позиция, допускаемая в Twenty по новым правилам. Без фильтра по `load_date`: дыра не ограничена одним диапазоном скана.

Позиции `TWENTY_RUCHNAYA` / ручные: не пересчитывать по словам. Если поле стало массивом — обернуть текущее значение (`null`/пусто → `["BRANDING"]`, иначе `[старый скаляр]`), чтобы запись не пропала с досок. Не добавлять чужие направления.

### Операция: отдельная задача `product-stream-backfill`

Не расширять bulk-resync и не звать полный `syncDealToTwenty` как основной путь.

Для каждой сделки:

1. Взять `deal_items`, посчитать `productStreams` по правилам выше.
2. Сматчить с Twenty line items как в обычном diff (имя / `twenty_id`).
3. **Update только поля набора потоков** у смэтчившихся PARSER-позиций. `ignoreStageProtection` для этого поля: поздняя стадия не должна блокировать возврат на реализацию.
4. Не удалять позиции. Не создавать отсутствующие в Twenty (это не чинит «уехавшие» записи; полный синк по-прежнему отдельная кнопка).
5. Не пересчитывать сумму opportunity. Не трогать print sheet.
6. Ошибка одной сделки: записать, идти дальше.

Конкуренция: 409, если уже идёт эта задача, bulk-resync или `decor-mk-scan`.

### UI

Настройки → Интеграции → Twenty CRM, рядом со сканом декора/МК:

- Заголовок: «Вернуть потоки на доски»
- Пояснение: пересчитать брендинг/декор/МК у уже синкнутых позиций; пересечения снова видны на обеих досках; позиции не удаляются.
- Превью: число сделок с `twenty_id` в выборке.
- Confirm по числу сделок, прогресс как у bulk-resync (done/total, updated, failed, ошибки).

Без диапазона дат: прогон по всем eligible synced-сделкам. Если объём пугает оператора — опциональный `from`/`to` по `load_date` **дополнительно**, дефолт = все. Дефолт «все» обязателен для закрытия дыры; узкий диапазон не должен быть единственным путём.

### Критерий готовности миграции

- Задача дошла до `completed` / `completed_with_errors` на проде (или staging, затем прод).
- Пример стойки: обе позиции содержат `BRANDING` **и** `DECOR` (если слова декора всё ещё в списке); заказ виден в реализации и в «МК и Декор».
- Выборочная проверка: позиции только с словами МК без брендинга **не** появились на реализации.
- Ручные позиции не пропали и не сменили направление из-за слов.

Деплой порядка:

1. Поле набора + доски понимают и массив, и старый скаляр как `[скаляр]` (`null`/`[]` не рисовать как брендинг).
2. Классификатор пишет набор; скан декора/МК пишет полный набор.
3. **Сразу** backfill на проде — без этого пересечения не появятся на реализации.
4. Новые записи больше не пишут скаляр.

Пункт 3 не откладывать «на потом»: без него задача не сделана.

## Ошибки

- Нет конфига Twenty — задача `failed` на старте.
- Twenty отклонил MULTI_SELECT payload — остановить и чинить маппинг; не считать миграцию успешной.
- Частичный прогон: повторный запуск идемпотентен (тот же набор → no-op update).

## Тесты

Парсер:

- Пересечение слов → набор содержит оба; не одно значение.
- Только MK / только DECOR / только брендинг.
- Блеклист МК не мешает `BRANDING` с того же имени.
- `include` без слов → `[BRANDING]`.
- `exclude` не в Twenty.
- Скан декора/МК update сохраняет `BRANDING` в наборе.

Доски:

- Фильтр по вхождению в набор, не по равенству.
- `null` не на реализации.
- Пересечение видно в обоих фильтрах (одна `id`).

Миграция:

- Скаляр `DECOR` + имя с брендинговым словом → в Twenty набор с `BRANDING` и `DECOR`.
- Регрессия имён из примера стойки.
- Ручная позиция с `MK` остаётся `[MK]`.
- Preview/POST 409 при активном bulk-resync / decor-mk-scan / другом backfill.
- Цикл не падает на первой ошибке сделки.

## Риски

- Смена типа поля в Twenty на проде: проверить на staging `yarn twenty apply` до backfill.
- Повторный старый скан декора/МК до фикса «полный набор» снова снимет брендинг. Фикс скана выкатывать **до** или **вместе** с backfill, не после.
- Двойной учёт в отчётах, если кто-то сложит итоги двух досок: это следует из «видно там и там», не баг.
