# Tony «свободная запись» — имя позиции из комментария

**Дата:** 2026-07-28  
**Статус:** Утверждён к написанию плана реализации  
**Ветка:** `staging` (crmparserv2)

## Проблема

В Tony есть каталожные позиции вида **«БРЕНДИНГ свободная запись ( КОМЕНТАРИЙ ОБЯЗАТЕЛЕН )»**.
Реальное описание позиции вводится в колонку **Комментарий** (например «ПВХ», «Наклейка на зеркало»).

После парсинга в Twenty две такие строки выглядят одинаково:

- `name` = шаблон «БРЕНДИНГ свободная запись…» у обеих;
- синк line items матчит по `normalizePattern(name)` → дубликаты схлопываются / перетирают друг друга;
- tip-rules / productStream / keywords смотрят на шаблон, а не на смысл из комментария.

Наблюдение на заказе (пример): в Tony две свободные записи с разными комментариями; в Twenty — две строки с одним и тем же комментарием, вторая уникальная позиция по сути потеряна.

## Цель

Для позиций «свободная запись»:

1. В локальных `deal_items` и в Twenty **`name` = текст комментария Tony**, если он непустой.
2. Поле **Комментарий** (`comment` / Twenty `kommentariy`) после нормализации — **пустое** (не дублировать текст, ставший названием).
3. Если комментарий пустой — оставить шаблонное имя как fallback.
4. ~~Классификацию / tip / productStream вести **только по новому `name`** (как у обычной позиции), без специального «всегда BRANDING».~~ **Заменено:** классификация free-entry всегда `keyword_match` — см. `2026-08-19-free-entry-whitelist-classification-design.md`. Tip-rules по-прежнему по новому `name`.

## Не в scope (v1)

- Стабильный id строки Tony (`tr[data-id]`) для матчинга при смене комментария.
- Разруливание двух free-entry с **одинаковым** текстом комментария.
- Изменение `parseTonyOrder` / HTML-селекторов (шум `info км: N файл` в `td` уже отсекается через `.item_name_link`).
- Миграция уже созданных «кривых» line items в Twenty (исправление — следующим ресинком после выкладки).

## Выбранный подход

**Нормализация в `buildTonyItems`** (не в парсере и не только на границе Twenty).

- `parseTonyOrder` остаётся верным HTML: `name` = каталог, `comment` = комментарий.
- Чистая функция (например `normalizeFreeEntryItem`) применяется к каждому item внутри `buildTonyItems`.
- Все пайплайны уже идут через `buildTonyItems`: `parser`, `import-by-booking`, `attach-tony-booking`, `historical-export`.

Отклонены:

- Перепись в `tony-parser` — смешивает DOM и бизнес-правило.
- Только на синке Twenty — локальные имена остаются шаблоном, `computeLineItemDiff` и classify ломаются как сейчас.

## Правило нормализации

Детект: `name` после trim содержит подстроку **`свободная запись`** (case-insensitive).

| Условие | Результат |
|---|---|
| Не free-entry | без изменений |
| Free-entry, `comment.trim()` непустой | `name = comment.trim()`, `comment = ''` |
| Free-entry, `comment` пустой / только пробелы | `name` = исходный шаблон, `comment = ''` |

Остальные поля (`price`, `quantity`, `discount`, `sum`, `quantity_num`, …) не трогаем.

## Поток данных

```
Tony HTML
  → parseTonyOrder          # сырой name/comment
  → buildTonyItems          # + normalizeFreeEntryItem
  → classifyItems / tip / productStream
  → deal_items + Twenty sync (match by name)
```

`tonyContentHash` по-прежнему хеширует **сырой** снимок `parseTonyOrder` (включая исходный comment) — смена комментария в Tony продолжает триггерить репарс.

## Идентичность и ресинк

После нормализации две free-entry с разными комментариями получают разные `name` → `computeLineItemDiff` создаёт/обновляет обе.

Смена текста комментария в Tony = смена `name` в нашей модели:

- старая Twenty-строка (если стадия позволяет удаление) попадёт в `toDelete`;
- новая — в `toCreate`.

Для v1 это приемлемо (без привязки к Tony `data-id`).

Две free-entry с **одинаковым** комментарием остаются коллизией по имени — как любые дубли каталога; отдельно не чиним.

## Ошибки и устойчивость

- Функция чистая, без I/O; сбоев рантайма не добавляет.
- Неверный детект (ложная подстрока в обычном названии) маловероятен; при необходимости позже сузить до точного/regex шаблона каталога.

## Тесты

В `backend/tests/tony-mapping.test.js` (и при необходимости unit на `normalizeFreeEntryItem`):

1. Free-entry + непустой comment → `name === comment`, `comment === ''`.
2. Free-entry + пустой comment → шаблонное имя без изменений.
3. Обычная позиция с comment → без изменений.
4. Две free-entry с разными comment → два разных `name` после `buildTonyItems`.

Существующий тест в `tony-parser.test.js` на `product_text_value` **не менять**: парсер по-прежнему отдаёт шаблон + comment.

## Критерий готовности

На заказе с ≥2 свободными записями с разными комментариями после парсинга/синка в Twenty:

- две позиции с именами = тексты комментариев Tony;
- поле Комментарий пустое;
- обе строки независимы (не одна перетёрла другую).
