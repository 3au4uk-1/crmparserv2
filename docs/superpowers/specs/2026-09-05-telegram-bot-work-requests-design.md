# Заявки обычного Telegram-бота: просчёты, разработка, проверка

**Дата:** 2026-09-05  
**Статус:** Утверждён дизайн в чате, ждёт ревью файла  
**Репозитории:** `crmparserv2` (Bot API, разбор формы, файлы, публикация в чат), `BrandingTwentyView` (объект, две доски, запрет пустого «Готовый», действие обновления)  
**Ветка:** `staging`

## Проблема

В трёх корпоративных форумах менеджеры тегают бота в топиках просчёта, разработки макетов и проверки. Заявки теряются в ленте: нет очереди, статуса и гарантированного ответа в том же месте, куда писали.

Параллельно в `crmparserv2` живут **два** Telegram-транспорта. Userbot уже закрывает дайджесты, пересылку своих упоминаний, auto-invite, оклейку и каталог чатов. Обычный бот почти только обнаруживает чаты и шлёт баннер подрядчику. Новый приём заявок нельзя вешать на оба канала — будут двойные карточки.

## Цели

- Обычный бот в девяти топиках (3 чата × 3 топика) принимает заявки по закреплённой форме и ведёт их в Twenty.
- Менеджер сразу видит одно сообщение бота; ответ появляется **в нём же** после стадии «Готовый».
- Исполнитель работает из канбана Twenty, не ищет сделку вручную, если бронь нашлась.
- Userbot не создаёт заявки и не отвечает шаблонами приёма. Свои старые функции (дайджест, форвард своего тега, инвайты, оклейка) не переносим на этого бота.

## Не в scope

- Перенос дайджестов, оклейки, auto-invite, mention-forward на Bot API.
- Fallback «тегнули userbot — создай ту же заявку».
- Автоподстановка макетов на печать; из заявки только переход в сделку.
- Приём по правке старого сообщения менеджера.
- Отдельные колонки «Отклонено», «Правки», «Запускаем».
- Девять досок (компания × тип). Разработка и проверка не расходятся на две воронки.
- Новое мобильное приложение или отдельная админка очереди вне Twenty / страницы Telegram в парсере.

## Решения, принятые с пользователем

- Отдельный объект заявок, не карточка сделки. Сделка привязывается при матче.
- Матч сделки: бронь (6 цифр) → при отсутствии брони точное имя сделки, если оно всё же есть в тексте. Нет однозначного матча — заявка без связи, оператор привязывает руками.
- Неполная форма: карточки нет. Бот перечисляет дыры и **явно** просит новое сообщение, не правку.
- Ответ в чат — одно свободное поле. Публикуется как есть.
- После «Готовый»: кнопка «Обновить в Telegram», повторный тег только по галке «Уведомить менеджера».
- Формы — копируемые закрепы (ниже). Дедлайн нигде не обязателен и из форм убран.
- Пустая ссылка на носитель + файл в том же сообщении (или альбоме) = ок.
- Бронь: ровно 6 цифр одним блоком (`123456`).
- Стадии: **Новый → В работе → Готовый**. Создание всегда в «Новый».
- В чат при создании: «принят, ответ появится в этом сообщении». Стадия «В работе» чат не трогает. «Готовый» публикует ответ и тегает менеджера.
- Два канбана одного объекта: Просчёты | Разработка/проверка (типы `макет` / `визуализация` / `проверка` разделены чипом).
- Заявки только у обычного бота. Userbot заявки Twenty из этих топиков не создаёт.
- Файлы ≤ 20 МБ — вложения карточки Twenty. Крупнее — ссылка на сообщение в Telegram, заявку не отвергаем.
- В «Готовый» без текста «Ответ в чат» переходить нельзя.

## Подход

Адаптер в `crmparserv2` + объект в Twenty. Twenty — источник правды для очереди, стадии и текста ответа. Парсер — единственный вход Bot API и единственный, кто пишет/правит сообщения бота в этих топиках.

Отклонено: вебхук Telegram сразу в Twenty (файлы, альбомы, конфиг топиков неудобны). Отклонено: истина в SQLite и зеркало в Twenty (стадии разъедутся).

```
Менеджер тегает бота в сконфигурированном топике
        ↓
crmparserv2 (webhook или уже существующий polling)
        ↓ отказ → reply: дыры + «напиши новое сообщение»
        ↓ успех
номер заявки → матч сделки → файлы → create в Twenty (Новый)
        ↓
одно reply: «Запрос #N принят. Ответ появится в этом сообщении.»
        ↓
Twenty: две доски
        ↓ переход в Готовый (ответ обязателен)
crmparserv2 edit того же сообщения + тег менеджера
        ↓
после Готовый: «Обновить в Telegram» ± уведомить
```

## Формы (закреп в топике)

`@бот` в закрепе заменить на username обычного бота. Ключи строк — контракт парсера, без переименования в коде.

Пустые значения: нет строки, пусто после `:`, `-`, `нет`, `файл`.

### Просчёты

```
@бот
Что посчитать:

```

Обязательно: `Что посчитать`. Фото и файлы — вложением к этому сообщению.

### Разработка — макет

```
@бот
Тип: макет
Бронь:
ТЗ:
Название позиции под брендинг:
Ссылка на логотип / шрифт / брендбук:

```

### Разработка — визуализация

```
@бот
Тип: визуализация
Бронь:
ТЗ:
Название позиции под брендинг:
Ссылка на макеты:
Ссылка на логотип / шрифт / брендбук:

```

Обязательно: `Тип` (`макет` или `визуализация`), `Бронь`, `ТЗ`, `Название позиции под брендинг`.  
Носитель: для макета — ссылка на логотип **или** фото/документ; для визуализации — ссылка на макеты **или** фото/документ. Вторая ссылка у визуализации (логотип/брендбук) не блокирует приём.

### Проверка

```
@бот
Бронь:
Комментарий: проверить
Ссылка на макеты:
Название позиции под брендинг:

```

Обязательно: `Бронь`, `Комментарий` (`проверить` или `запускаем`), `Название позиции под брендинг`, ссылка на макеты **или** фото/документ.

## Разбор и валидация

Бот обрабатывает сообщение только если:

1. `chat_id` + `message_thread_id` есть в конфиге девяти слотов;
2. в тексте или entities есть явный тег **обычного** бота;
3. это не сообщение самого бота и не сервисный апдейт.

`edited_message` и правки менеджера игнорируются. Тип заявки задаёт **роль топика** в конфиге. В топике разработки дополнительно обязателен `Тип:` из формы.

**Бронь.** После `Бронь:` trim, затем ровно `/^\d{6}$/`. Иначе отказ с примером `123456`. Не принимаем `123-456`, `бронь 123456`, 5 цифр.

**Ссылка или файл.** Нормальный URL (строка с `http://` или `https://`) — поле ок без вложения. Нет URL, но в этом сообщении или в альбоме с тем же `media_group_id` есть photo/document — поле ок, файлы идут на карточку. Нет ни URL, ни файла — отказ: «Нужна ссылка или файл в этом же сообщении.» Есть и ссылка, и файлы — берём оба.

**Альбом.** Форма в caption первого сообщения. Бот ждёт остальные элементы группы (короткое окно, порядка 1 с), затем валидирует один раз. Голосовые и стикеры носителем не считаются.

**Матч сделки.**

1. Если в заявке есть валидная бронь — ищем Opportunity в Twenty, в чьём `name` это 6-значное число стоит отдельным числом (не часть более длинного). Уже используемый на доске разбор брони из имени (`extractBookingId`) — ориентир, но для этой фичи ищем **ровно эти 6 цифр**. Ровно одна сделка — связь. Ноль или несколько — связь пустая, бронь на карточке остаётся.
2. Если брони нет (просчёт) и в тексте есть необязательная строка `Сделка:` — точное совпадение с `opportunity.name`. Иначе без связи.

Подстановка макетов на печать остаётся ручной в карточке сделки; заявка даёт переход в сделку в один клик.

## Объект Twenty

Имя API: `telegramRequest`. Подпись: **Заявки бота**. Индексная таблица + две kanban-view + два пункта бокового меню. Технический объект без view делать нельзя.

**Стадия** (`stage`, SELECT): `NEW` «Новый», `IN_PROGRESS` «В работе», `DONE` «Готовый».

**Тип** (`kind`, SELECT): `QUOTE` «просчёт», `LAYOUT` «макет», `VISUAL` «визуализация», `REVIEW` «проверка».

Доски:

| View | Фильтр | Группировка |
|---|---|---|
| Просчёты | `kind = QUOTE` | `stage` |
| Разработка / проверка | `kind IN (LAYOUT, VISUAL, REVIEW)` | `stage` |

**Поля, которые видит человек**

| Поле | Назначение |
|---|---|
| `name` | `Запрос #N` |
| `requestNumber` | целое N, выдаёт парсер |
| `stage`, `kind` | воронка и чип |
| `company` | подпись компании из слота чата |
| `replyText` | «Ответ в чат» |
| `requesterName`, `requesterUsername` | кто тегнул |
| `telegramMessageUrl` | ссылка на сообщение бота |
| `brief` | «Что посчитать» или ТЗ |
| `booking` | 6 цифр или пусто |
| `opportunity` | MANY_TO_ONE на сделку, можно поправить руками |
| `positionName` | название позиции под брендинг |
| `logoOrBrandUrl` | ссылка на логотип / шрифт / брендбук |
| `layoutsUrl` | ссылка на макеты |
| `reviewAction` | `проверить` / `запускаем` |
| `largeFileUrls` | TEXT: ссылки на файлы тяжелее 20 МБ и на исходный тег |
| `notifyOnRepublish` | галка «Уведомить менеджера», по умолчанию false |
| вложения Twenty | скачанные файлы ≤ 20 МБ |

`chat_id`, `message_id` тега, `message_id` ответа бота, `user_id` менеджера, `media_group_id` живут в SQLite парсера. Без строки связки публикация в чат невозможна.

## Поведение в чате

Отказ (карточки нет) — одно reply. Список конкретных дыр. Последняя строка всегда:

`Не редактируй это сообщение — напиши новое с формой и тегом.`

Успех — одно reply:

`Запрос #42 принят. Ответ появится в этом сообщении.`

Это сообщение бот позже редактирует. «В работе» его не меняет.

«Готовый»: `editMessageText` на текст `replyText` + mention менеджера (text mention по `user_id`, иначе `@username`). Reply-to исходного тега сохраняем, чтобы ветка в топике не рвалась.

«Обновить в Telegram»: тот же `editMessageText`. Mention — только если `notifyOnRepublish` включена в момент действия. Стадию не меняем.

Если Twenty не создала запись — в чат нет «принят». Текст: `Не удалось взять в работу, напиши новое сообщение через минуту.`

Новый тег = новая заявка, даже с той же бронью. Повтор доставки того же `chat_id + message_id` (или того же `media_group_id`) карточку не дублирует.

## Конфиг девяти слотов

На странице `/telegram` в парсере: список слотов `{ chatId, threadId, companyLabel, topicRole }`.  
`topicRole`: `QUOTE` | `DESIGN` | `REVIEW`.  
`DESIGN` — топик разработки (и макет, и визуализация).

Слот не заполнен — бот в этом топике молчит. Деплой для смены чатов не нужен. Userbot-обработчики (mention-forward, digest commands) не регистрируются на эти `chatId+threadId` как на источник заявок; если userbot тегнули там — он ведёт себя как в любом другом чате только для **своих** старых функций (форвард упоминания userbot-аккаунта), заявку Twenty не создаёт.

## Публикация из Twenty

Паттерн как у оклейки: logic function / command menu в `BrandingTwentyView` → HTTP в `crmparserv2`.

1. Смена `stage` на `DONE` при непустом `replyText` → публикация + тег.
2. Смена на `DONE` при пустом `replyText` → отказ (карточка остаётся в прежней стадии).
3. Действие «Обновить в Telegram» доступно только при `DONE` и непустом `replyText`.

Если Telegram не принял edit (бот кикнут, сообщение удалено) — стадия уже `DONE`, на карточке видна ошибка публикации, повтор — кнопкой обновления.

## Ошибки

| Ситуация | Чат | Карточка |
|---|---|---|
| Дыры формы / бронь / нет носителя | дыры + «напиши новое» | нет |
| Twenty create упал | «напиши новое через минуту» | нет |
| Файл > 20 МБ | заявка принимается | URL в `largeFileUrls`, не вложение |
| Часть файлов не скачалась | принят | нескачанные — строками в `largeFileUrls`, успешные ≤ 20 МБ остаются вложениями |
| Бронь не матчится / несколько сделок | принят | `opportunity` пустой |
| Публикация после DONE упала | без новой правки | ошибка, кнопка обновления |
| Нет строки SQLite | — | ошибка «нет связки с чатом» |
| Тег в неизвестном топике | молчание | нет |
| Тег userbot в этих топиках | заявка не создаётся | нет |

## Идемпотентность

- Вход: `update_id` + `chat_id` + `message_id`; для альбома — `chat_id` + `media_group_id`.
- Выход: повторный вход в `DONE` с тем же `replyText` не шлёт второй тег. Повтор «Обновить» без галки уведомления не тегает.

## Тесты

Автотесты без живого Telegram:

- парсер каждой формы: успех и все обязательные дыры;
- бронь: только `^\d{6}$`;
- `проверить` / `запускаем`;
- ссылка или файл, пустые синонимы, альбом;
- тексты отказа содержат «напиши новое»;
- матч сделки: одна / ноль / несколько;
- идемпотентность апдейта и альбома;
- повторный `DONE` с тем же текстом не тегает;
- пустой `replyText` → стадия не `DONE`;
- userbot не создаёт `telegramRequest`.

Ручной прогон на staging, один чат × три топика: отказ, приём, «В работе» без правки чата, «Готовый» с тегом, обновление с галкой и без, файл вместо ссылки, битая бронь, файл > 20 МБ.

## Компоненты реализации (ориентир)

**crmparserv2**

- Расширить inbound/polling: не только discovery, а обработчик упоминаний в слотах.
- Парсер формы, сбор альбома, загрузка файлов, выдача `requestNumber`.
- Таблица связки заявка ↔ Telegram.
- UI слотов на `/telegram`.
- HTTP endpoint публикации/обновления для Twenty.
- Явный запрет: код userbot не создаёт заявки и не отвечает шаблонами этого спека.

**BrandingTwentyView**

- `yarn twenty dev:add` для объекта, полей, двух view, двух navigation menu items, logic function / command menu.
- Связь на `opportunity`.
- Валидация перехода в `DONE`.

Все новые UUID — UUID v4.
