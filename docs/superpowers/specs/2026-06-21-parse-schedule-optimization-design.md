# Оптимизация расписания парсинга — дизайн

**Дата:** 2026-06-21  
**Статус:** Ожидает ревью перед планом реализации  
**Связанные документы:** `2026-06-20-parsing-optimization-design.md` (параллелизация загрузки)

## Контекст и проблема

Сейчас парсинг по расписанию — **один cron** из настройки `parse_schedule` (дефолт `0 18 * * *`), каждый запуск всегда парсит **сегодня → +14 дней** (`getDefaultParseRange()`).

Недостатки:

- Сделки почти не меняются ночью и редко в выходные — ежедневный полный прогон в нерабочее время лишний.
- Один раз в день (18:00) — слишком редко для актуальности в рабочие часы.
- Один cron не разделяет «когда» и «насколько далеко».

После параллелизации загрузки (~30–60 с на ~200 заказов) частые узкие прогоны становятся практичными; `content_hash` дополнительно снижает работу на неизменённых сделках.

## Цель и нецели

**Цель:** заменить единый cron на **time-aware расписание** с разными горизонтами парсинга по времени суток и дню недели, зашитое в код.

**Нецели:**

- Не меняем логику парсинга, сверки Tony, синка Twenty.
- Не добавляем UI для редактирования расписания (правила фиксированы в коде).
- Не вводим change-detection в этой итерации.
- Не меняем ручной парсинг (произвольный диапазон через API/UI).

## Согласованные правила (tiers)

Часовой пояс: `CRM_TIMEZONE` (`Europe/Moscow` по умолчанию).

| Tier | Когда (МСК) | Интервал | Окно парсинга |
|------|-------------|----------|---------------|
| `weekday-fast` | Пн–Пт, 9:00–21:00 | каждый час (9, 10, …, 21) | +4 дня от сегодня |
| `weekday-deep` | Пн–Пт, 22:00 | раз в день | +14 дней от сегодня |
| `night-light` | каждый день, 2:00 | раз в день | +2 дня от сегодня |
| `weekend` | Сб–Вс, круглосуточно | каждые 2 часа (0, 2, 4, …, 22) | +7 дней от сегодня |
| — (тишина) | 22:00–9:00, кроме 2:00 и 22:00 (будни) | нет автообновлений | — |

**Приоритет при совпадении** (один прогон за тик):

1. `weekday-deep` (+14)
2. `weekend` (+7) — перекрывает `night-light` в 2:00 в выходные
3. `weekday-fast` (+4)
4. `night-light` (+2)

Примеры:

- Сб 2:00 → один прогон `weekend` (+7), не два.
- Пт 22:00 → `weekday-deep` (+14).
- Пт 2:00 → `night-light` (+2).
- Пт 3:00–8:00 → тишина (нет tier).

## Выбранный подход

**Подход B — один cron-тик + резолвер расписания.**

Один cron каждые **15 минут** (`*/15 * * * *`). На каждом тике `resolveParseTier(now)` определяет, нужен ли прогон и какой tier применить. Тик 15 минут, а не 60: резолвер проверяет попадание в часовой слот, чтобы не пропустить запуск после рестарта сервера.

### Отклонённые альтернативы

- **Multi-cron (несколько выражений):** проще декларативно, но в 2:00 в выходные срабатывают и `night-light`, и `weekend` без дополнительной логики; сложнее централизовать mutex.
- **Multi-cron + mutex:** дублирует tier-логику в нескольких callback'ах.

## Архитектура

```
backend/src/services/scheduler.js
  └─ cron */15 * * * *  (timezone: CRM_TIMEZONE)
       └─ resolveParseTier(now) → tier | null
            └─ if tier && !isParsingInProgress()
                 └─ runParsing(getParseRangeForTier(tier, now))
```

Новый модуль (рекомендуется для тестируемости):

- `backend/src/services/parse-schedule.js` — константы tiers, `resolveParseTier`, делегирует диапазоны в `crm-dates.js`

Расширение `backend/src/utils/crm-dates.js`:

- `getParseRangeForTier(tier, now)` — `{ start, end }` для каждого tier (start всегда ≥ начало сегодня, как `getMinParseStart`)
- `getDefaultParseRange(now)` — **без изменений** (используется ручным парсингом и API `/defaults`)

## Mutex и пропуски

- Флаг `parsingInProgress` сейчас локален в `backend/src/routes/parsing.js`. **Вынести** в общий модуль (например `backend/src/services/parsing-lock.js`) и использовать и в API, и в scheduler.
- Если парсинг уже идёт — scheduler **пропускает** тик без очереди.
- Пропущенный слот (долгий прогон) **не догоняется** — следующий слот подхватит.
- Ручной парсинг при занятости — по-прежнему HTTP 409.

## Миграция настроек и UI

- Scheduler **не читает** `parse_schedule`.
- Поле «Cron-выражение» в `frontend/src/pages/Settings.jsx` — **удалить** (чтобы не вводить в заблуждение).
- Ключ `parse_schedule` в БД можно оставить (безвредный orphan) или удалить из `schema.sql` для новых установок — не критично.
- Валидация `parse_schedule` в `backend/src/routes/settings.js` — удалить.

## Наблюдаемость

- Лог при запуске: `[scheduler] tier=weekday-fast range=2026-06-21..2026-06-25`.
- Лог при пропуске из-за mutex: `[scheduler] skipped tier=weekday-fast (parsing in progress)`.
- Запись tier в `parse_runs` — **не в этой итерации** (YAGNI); достаточно логов.

## Оценка нагрузки

- Будни: ~13 `weekday-fast` + 1 `weekday-deep` + 1 `night-light` ≈ **15 прогонов/день**.
- Выходные: **12** прогонов `weekend`/день (каждые 2 ч).
- Реальная нагрузка ниже за счёт `content_hash` skip и узких окон днём.

## Связь с параллелизацией

Независимые изменения; синергия: после `PARSE_PIPELINE=parallel` часовой режим +4 дня укладывается в ~30–60 с.

## Тестирование

Юнит-тесты `parse-schedule.js` (и при необходимости `getParseRangeForTier`) на фиксированных `now`:

| Момент (МСК) | Ожидаемый tier |
|--------------|----------------|
| Пт 10:00 | `weekday-fast` |
| Пт 21:00 | `weekday-fast` |
| Пт 22:00 | `weekday-deep` |
| Пт 2:00 | `night-light` |
| Пт 3:00–8:00 | `null` |
| Сб 2:00 | `weekend` (не `night-light`) |
| Сб 14:00 | `weekend` |
| Вс 23:00 | `null` (не попадает в слот 0,2,4…22) |

Тесты диапазонов: `weekday-fast` → +4 дня, `weekday-deep` → +14, `night-light` → +2, `weekend` → +7; start ≥ начало сегодня.

Интеграционный smoke: scheduler не стартует второй прогон при `parsingInProgress === true`.

## Риски

- **Пропуск ночных правок 22:00–9:00:** mitigated `night-light` в 2:00 (+2 дня) и ручной парсинг.
- **Перезапуск в слоте:** 15-минутный тик + проверка «текущий час в списке слотов tier'а» — прогон всё равно произойдёт в пределах часа.
- **День недели в UTC vs Moscow:** вся логика через `Intl` / `CRM_TIMEZONE`, как в `crm-dates.js`.
