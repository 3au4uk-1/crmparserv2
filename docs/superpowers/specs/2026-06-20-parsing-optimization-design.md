# Оптимизация парсинга (параллелизация загрузки) — дизайн

**Дата:** 2026-06-20
**Статус:** Утверждён к написанию плана реализации
**Ветка разработки:** уточнить перед стартом (тестируем локально, на прод не выкатываем до подтверждения)

## Контекст и проблема

После того как Tony стал источником истины по заказу (см. `2026-06-19-tony-order-source-design.md`),
время прогона резко выросло:

- Раньше (только календарь): ~**230с** на 2 недели вперёд.
- Сейчас (с Tony): ~**1000с** на 4 дня вперёд, ~**200 заказов** → ~5с на заказ.

Парсер (`backend/src/services/parser.js → runParsing`) работает **строго последовательно**: один внешний
цикл по событиям календаря, внутри которого по очереди выполняются сетевые запросы, парсинг, сверка,
запись в БД и синк в Twenty. Узкое место — **последовательный сетевой I/O с искусственными паузами**, а не
парсинг HTML и не запись в БД.

### Где уходит время (на 1 заказ Tony)

`fetchTonyOrderHtml` (`backend/src/services/tony-client.js`) на каждый заказ делает ~10 запросов по очереди,
с паузой `TONY_REQUEST_DELAY_MS` (350мс) между ними:

- 1× `GET /orders/orders_edit/?id=` — страница заказа (даты, адрес).
- 8× `POST /ajax/order_products_list.php` с `actionVar=<category>` (food, products, tech, personnel,
  services, assembly, transport, expense).
- 1× `POST /ajax/order_sklad_list.php`.

Плюс на каждое событие: пауза 350мс + `POST cal_description.php` (описание из календаря), и LLM-классификация
неопознанных позиций.

## Результаты исследования (HAR живой страницы заказа)

Проанализирован HAR со страницы заказа `160059` (170 запросов всего). Выводы:

1. **Единого «bulk» эндпоинта нет.** Каждая категория грузится отдельным `order_products_list.php` с разным
   `actionVar`. Объединить в один запрос нельзя → рычаг = **параллельность**, а не консолидация.
2. **Сервер отвечает быстро:** все ответы 200, ~100–260мс на AJAX, страница заказа ~890мс / 627 КБ. Ни одного
   429 в выборке. Значит паузы 350мс — **чистый оверхед**, почти удваивающий время на заказ.
3. **Все ~10 запросов заказа независимы:** AJAX-вызовы требуют только `id` + куки, не зависят ни друг от друга,
   ни от предварительной загрузки страницы. Их можно тянуть **полностью параллельно**. Тогда время заказа ≈
   время самого тяжёлого запроса ≈ **~0.9с** (упор в 627 КБ страницы) вместо ~5.5с.
4. Браузер шлёт много лишнего (`offers_sklad_qnt` 21×, `order_products_sum`, transport, gabarits,
   profitability) — это UI-пересчёты при редактировании. Наш парсер их не трогает (и правильно).

**Оговорка по лимитам:** гарантий отсутствия серверного rate-limit нет (в выборке 429 не было, но это лишь один
заказ). Поэтому конкурентность делаем **настраиваемой**, стартуем консервативно и закладываем адаптивный backoff.

## Цель и нецели

**Цель:** сократить время прогона с ~1000с до ориентира **~30–60с** на 200 заказов, не меняя результат
(итоговое состояние `deals`/`deal_items`/Twenty должно совпадать с текущим поведением).

**Нецели:**

- Не меняем логику сверки (`tony-reconcile.js`), маппинга (`tony-mapping.js`), парсеров HTML/титула,
  классификации по существу.
- Не меняем семантику синка/отмены в Twenty (у него свой rate-limiter, остаётся последовательным).
- Не вводим change-detection/пропуск неизменённых заказов в этой итерации (рискованно без надёжной метки
  изменения из Tony; вынесено в «Будущая работа»).

## Выбранный подход

**Подход B — разделение на две фазы: параллельный prefetch + последовательное применение.**

### Фаза 1 — Prefetch (параллельно, под общим лимитером)

Для всех событий в диапазоне параллельно (с ограничением конкурентности) загружаем **сырые сетевые данные** и
прогоняем чистый (CPU) парсинг, складывая результат в память:

```
eventId → {
  bookingNumbers,                            // extractBookingNumbers(title)
  descHtml, calParsed,                       // cal_description.php + parseDealDescription(descHtml)
  tonyOrders: Map<bookingNumber, parsedOrder> // parseTonyOrder(html); только успешно загруженные
}
```

- Внутри одного заказа: **сначала** загружается страница `orders_edit` (это гейт для 404/редиректа — на
  несуществующий заказ не шлём лишние запросы), затем все ~9 запросов категорий
  (`order_products_list` × 8 + `order_sklad_list`) запускаются **параллельно**. Per-order ≈ страница +
  max(категория) ≈ ~1.1с вместо ~5.5с.
- Все исходящие CRM+Tony запросы проходят через **общий семафор** (глобальная граница конкурентности), чтобы
  не было взрыва «200 заказов × 9 = ~1800 одновременных». Кросс-заказное перекрытие даёт основной выигрыш.
- **Классификация (LLM) в этой фазе НЕ выполняется.** Она остаётся в фазе apply и гейтится по `content_hash`
  (как сейчас), чтобы не гонять LLM для неизменённых сделок и не раздувать стоимость. Батч-классификация —
  «Будущая работа».
- `tonyOrders` содержит запись только для успешно загруженных заказов (как текущий `resolveTonyOrders`): и 404,
  и сетевая ошибка → записи нет → в apply отрабатывает существующий фолбэк на календарь / сохранение старых
  Tony-данных.

### Фаза 2 — Apply (последовательно, детерминированно)

Идём по событиям в том же отсортированном порядке, что и сейчас, и выполняем **существующую** логику
(`planEventReconciliation`, relink, `classifyItems`, insert/update `deals`+`deal_items`, отмена, постцикловый
resync/cancel в Twenty, `processAutoApprovals`) — но читаем уже загруженные сетевые данные из карты фазы 1
вместо сетевых вызовов inline. `classifyItems` вызывается здесь, после проверки `content_hash` (как сейчас).

**Почему так:** запись в better-sqlite3 синхронная и быстрая; параллелить нужно только сеть. Разделение
сохраняет порядок и корректность записи 1-в-1 с текущим поведением и исключает гонки за БД/Twenty.

### Отклонённые альтернативы

- **A (только параллель внутри заказа):** проще, но оставляет внешний цикл последовательным (~200с потолок).
  Поглощается подходом B как частный случай.
- **C (change-detection / пропуск неизменённых):** наибольший потенциал на инкрементальных прогонах, но
  рискован без надёжной метки изменения из Tony — событие календаря может не меняться, а заказ измениться.
  Вынесено в «Будущая работа».
- **Bulk-эндпоинт Tony:** недоступен (подтверждено HAR).

## Компоненты

- **`backend/src/services/fetch-pool.js` (новый):** асинхронный семафор/лимитер конкурентности (p-limit-стиль,
  без внешней зависимости). Параметры: макс. конкурентность и опциональный минимальный интервал (spacing) на
  слот. Плюс хелпер `withRetry` (экспоненциальный backoff + джиттер на 429/5xx/сеть). Один общий пул на
  CRM+Tony запросы.
- **`backend/src/services/tony-client.js`:** `fetchTonyProductTables` и `fetchTonyOrderHtml` переписываются на
  параллельную загрузку категорий через пул; убираются последовательные `setTimeout`-паузы.
- **`backend/src/services/parser.js`:** `runParsing` рефакторится в две фазы — `prefetchAll(events, …)` →
  карта, затем существующий цикл применения читает из карты. Поведение записи не меняется.
- **`backend/src/config.js`:** новые env (см. ниже).
- **Адаптивный backoff (`withRetry`):** при HTTP 429 / 5xx / сетевой ошибке — повтор с экспоненциальной паузой
  и джиттером (ограниченное число попыток). Редирект на логин (истёкшая сессия) в v1 сохраняет **текущее**
  поведение: ошибка по конкретному заказу/описанию → запись в карту не попадает → фолбэк на календарь / скип
  (как сейчас в `catch` у `resolveTonyOrders`/`fetchDescription`). Сериализованная mid-run переавторизация —
  «Будущая работа».

## Конфигурация (env)

- `FETCH_CONCURRENCY` — макс. одновременных CRM+Tony запросов. Дефолт консервативный (например, `4`).
  **В parallel-режиме «нежность» к серверу обеспечивает именно лимит конкурентности**, а не паузы.
- `TONY_REQUEST_DELAY_MS` — остаётся только для **legacy-режима** (паузы между последовательными запросами). В
  parallel-режиме НЕ применяется как глобальный spacing (иначе он задросселирует пул и съест выигрыш). `spacing`
  у пула — опциональный параметр, по умолчанию `0`.
- `PARSE_PIPELINE` (флаг) — переключатель `legacy` (текущий последовательный) ↔ `parallel` (новый конвейер) для
  безопасного сравнения и быстрого отката.

## Корректность и риски

- **Общая сессия/куки** (module-level в `auth.js`/`tony-auth.js`): параллельное чтение безопасно;
  переавторизация в середине прогона сериализуется одним in-flight promise.
- **Память:** ~200 заказов HTML одновременно — приемлемо; при росте объёма обрабатывать чанками (диапазон
  событий бить на батчи).
- **Идентичность результата:** фаза 2 не меняет логику → состояние БД/Twenty совпадает с legacy при тех же
  входных данных. Это проверяется тестом (ниже).
- **Неизвестные лимиты:** консервативный дефолт + адаптивный backoff + лёгкий тюнинг через env; флаг
  `PARSE_PIPELINE=legacy` как мгновенный откат.
- **Порядок ошибок:** ошибка загрузки одного заказа/описания не должна валить весь прогон — фиксируем в карте
  как «ошибку для этого target» и в фазе 2 ведём себя как при текущем `catch` (скип/сохранение старых данных).

## Наблюдаемость

- Логи по фазам: длительность prefetch и apply, число запросов, фактическая пиковая конкурентность, число
  backoff/повторов.
- Сохранять сводку тайминга в `parse_runs` (опционально), чтобы тюнить `FETCH_CONCURRENCY` по реальным прогонам.

## Тестирование

- Юнит-тесты `fetch-pool.js`: соблюдение лимита конкурентности, spacing, поведение backoff на смоделированных
  429.
- Юнит-тесты обновлённого `tony-client.js`: параллельная сборка тех же category-таблиц, что и раньше
  (результирующий HTML/набор позиций эквивалентен последовательной версии) — на моках axios.
- **Golden-тест эквивалентности:** на фиксированном наборе замоканных событий/описаний/заказов состояние
  `deals`+`deal_items` после `parallel`-конвейера идентично `legacy`.
- Тест адаптивного backoff: при инъекции 429 запросы повторяются и прогон завершается успешно.

## Ожидаемый эффект

- Параллель внутри заказа: ~5.5с → ~0.9с на заказ (×~6).
- Кросс-заказная параллель (пул 4–6): ориентир **~30–60с** на 200 заказов против ~1000с (×~15–30).

## Будущая работа (вне этой итерации)

- Change-detection / пропуск неизменённых заказов (нужна надёжная метка изменения из Tony).
- Более лёгкий источник дат/адреса вместо 627 КБ страницы `orders_edit`, если найдётся.
- Батч-классификация LLM по нескольким заказам одним запросом (под `LLM_CONCURRENCY`).
- Сериализованная mid-run переавторизация при истечении сессии Tony/CRM.
